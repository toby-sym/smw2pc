# Playing and saving

Open settings with F2 or the cog. The Player tab contains volume, mute, focus pause,
quick save/load, the save folder, and compatibility report export.

| Shortcut | Action |
| --- | --- |
| F1 | Open ROM |
| F2 | Settings |
| F5 | Quick save |
| F8 | Load quick save |
| F9 | Pause/resume the entire player, including audio |
| F10 | Mute/unmute |
| F11 | Toggle fullscreen |

App shortcuts are reserved during keyboard rebinding. Enter remains the game's
Start button. Focus pause is enabled by default and can be disabled in Player settings.
The volume row sets volume from 0–100% according to where you click.

## Saves and preferences

Normal in-game saves now use cartridge SRAM. Changed SRAM is written every two
seconds, on game replacement, and at exit. This preserves the game's normal save
rules: it does not automatically save level progress that the game has not saved.

Each ROM's normalized SHA-256 identifies its folder under
`%LOCALAPPDATA%/SMW2PC/roms/<SHA256>/`:

| File | Contents |
| --- | --- |
| `save.srm` | Raw cartridge SRAM; compatible SRAM files can be copied here while the game is closed |
| `quicksave.state` | CPU, RAM, cartridge SRAM, video, controllers, SPC700, DSP and pending audio |
| `settings.json` | Controls, volume, window size, aspect ratio, cap, fullscreen and focus pause |
| `compatibility-report.json` | Build metadata and the last exported execution information |

Files are replaced atomically and the previous version is retained as `.bak`.
Validated backups are used if a primary save or settings file is unreadable.
Quick saves are bound to their ROM hash and snapshot format version. Loading one
also restores its SRAM. Future state format changes may require a new quick save;
raw `.srm` files remain independent of that format.

A new ROM inherits global preferences, then saves its own preferences. ROMs with
and without a copier header share the same profile when their normalized bytes match.
`SMW2PC_DATA_DIRECTORY` can select a different data directory, including a portable
folder. Recent ROM paths are shared with the builder; the builder shows the last three
available files and lets you select one to rebuild.

## Compilation reports

The builder shows live progress and writes `SMW-compatibility.html` and
`SMW-compatibility.json` beside the generated executable. Open the HTML report using
the builder's “Open last build report” link. It lists discovered code by bank, audio
entries, writable code variants, unresolved static transfers and verification status.

Discovered byte counts are not a whole-game compatibility percentage. ROMs also
contain graphics, music and tables. An uncompiled path still stops execution and
writes a per-ROM compatibility report with its CPU address.

## Repeatable gameplay checks

`./tools/test-homebrew-gameplay.ps1` builds original PAL and NTSC test ROMs locally,
compiles strict players, audits the absence of runtime translators, and compares
scripted state, rendered video, audio hashes and sample counts with committed baselines.
The test ROM uploads its original audio program through the SPC700 boot protocol and
uses controller input, SRAM, scrolling and color registers. Commercial ROMs and assets
are not used by this check. CI runs it on Windows, Linux and macOS; this checks the
managed compiled gameplay path, while platform packaging stays in its platform branch.
Homebrew captures and test results are uploaded only for dev builds. Release checks
still run, but homebrew fixtures, test tools and captures are excluded from release
packages and GitHub Releases.

On Windows, `./tools/test-player-ui.ps1` additionally exercises the SDL player with
dummy video/audio devices, isolated saves, actual key/mouse events and panel captures.
Run the gameplay preparation first. Neither helper is included in generated games.

To run your own local input replay with a ROM-specific player:

```powershell
./SMW.exe --verify --replay input.json --expect expected.json --report actual.json
```

The script contains `FormatVersion: 1`, the normalized `RomSha256`, `Frames`,
`CheckpointEvery`, and an `Inputs` list. Events use zero-based `Frame` values and
numeric `Buttons`/`PlayerTwo` masks from `SnesControllerButtons`; input is held until
the next event. Omit `--expect` to record a baseline. See `tests/Fixtures/*.replay.json`
for examples. `--screenshot final.bmp` captures the final frame. Replay metadata must
match the baseline, and any state, video, audio or sample-count mismatch fails the run.

After an intentional fixture or behavior change, update baselines explicitly with:

```powershell
dotnet run --project tools/GameplayChecks -c Release -- --record-baselines tests/Fixtures
```

Review those changes before committing them. Baselines are never regenerated by CI.
